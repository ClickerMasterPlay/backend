# Игровая логика и контракт взаимодействия с бэкендом

Документ описывает актуальные правила взаимодействия фронтенда с backend API
для игрового поля, баланса, инвентаря, предметов, покупок, машин и заданий.

## 1. Общие правила

Базовый путь API: `/api/v1`.

После создания гостя, регистрации или входа фронтенд получает `userId`. Во всех
запросах, относящихся к конкретному игроку, его нужно передавать заголовком:

```http
X-User-Id: <uuid>
```

На текущем этапе этот заголовок является идентификатором игрока, а не полноценным
токеном авторизации. После появления JWT или сессий контракт идентификации нужно
будет пересмотреть.

Сервер является единственным источником истины для:

- баланса кредитов;
- ресурсов;
- базовой и эффективной силы клика;
- содержимого инвентаря;
- экипированного инструмента;
- состояния машин;
- текущего блока и его HP;
- прогресса и наград заданий.

Фронтенд может выполнять оптимистичную анимацию, но после любого изменяющего
запроса должен заменить локальное состояние значениями из ответа сервера.

Стандартная ошибка имеет вид:

```json
{
  "error_code": "INSUFFICIENT_FUNDS",
  "message": "Insufficient credits: required 250, available 100",
  "timestamp": "2026-11-09T10:00:00Z"
}
```

Основные статусы:

- `400` — некорректный запрос или обязательный заголовок;
- `404` — пользователь, предмет, прогресс или задание не найдены;
- `409` — конфликт состояния, недостаточно средств, повторная покупка или награда;
- `429` — пакет кликов отправлен слишком часто;
- `500` — внутренняя ошибка, которую нельзя исправить изменением запроса.

## 2. Рекомендуемая начальная синхронизация

После получения `userId` фронтенду рекомендуется параллельно запросить:

1. `GET /api/v1/progress/me` — профиль, базовая сила и экипированный инструмент;
2. `GET /api/v1/economy/balance` — кредиты и ресурсы;
3. `GET /api/v1/inventory` — инструменты и машины;
4. `GET /api/v1/shop/catalog` — доступные товары и актуальные цены;
5. `GET /api/v1/game/current-block` — текущий блок;
6. `GET /api/v1/challenges` — задания и их глобальный прогресс.

Цены, коэффициенты и награды нельзя считать доверенными, если они пришли только
из локального каталога фронтенда. Для отображения магазина нужно использовать
серверный каталог, а окончательные значения брать из ответа операции.

## 3. Баланс и ресурсы

```http
GET /api/v1/economy/balance
X-User-Id: <uuid>
```

Пример ответа:

```json
{
  "credits": 400,
  "resources": {
    "stone": 12,
    "iron": 2
  }
}
```

`credits` используются для покупок и выдаются за разрушение блоков и задания.
`resources` — отдельный инвентарь добытых материалов. Ресурсы не заменяют
кредиты и сейчас не расходуются магазином.

## 4. Игровое поле и блоки

### Получение текущего блока

```http
GET /api/v1/game/current-block
X-User-Id: <uuid>
```

Блок содержит `type`, `rarity`, `currentHp` и `maxHp`.

### Отправка кликов

```http
POST /api/v1/game/click-batch
X-User-Id: <uuid>
Content-Type: application/json

{
  "clientBatchId": "<uuid>",
  "clicks": 10
}
```

В одном пакете разрешено от 1 до 50 кликов. Для каждой логической операции
фронтенд генерирует новый `clientBatchId`.

Если ответ потерян, запрос нужно повторить с тем же `clientBatchId` и тем же
значением `clicks`. Сервер вернёт сохранённый ответ и не начислит награду или
прогресс задания повторно. Использование того же идентификатора с другим числом
кликов возвращает `IDEMPOTENCY_KEY_REUSED`.

Урон рассчитывается так:

```text
ceil(clicks × baseClickPower × toolMultiplier)
```

Один пакет сейчас может разрушить не более одного блока. Избыточный урон не
переносится на следующий блок.

Ответ содержит:

- `destroyed` — был ли разрушен блок;
- `block` — актуальный блок после операции;
- `rewards` — награда именно этой операции;
- `balance` — полный актуальный баланс.

### Прогрессия блоков

Тип следующего блока определяется общим количеством разрушенных блоков:

| Разрушено | Тип | Редкость | HP | Кредиты | Ресурс |
|---:|---|---|---:|---:|---|
| 0–4 | `stone` | `COMMON` | 10 | 1 | `stone ×1` |
| 5–14 | `iron` | `UNCOMMON` | 25 | 3 | `iron ×1` |
| 15–29 | `gold` | `RARE` | 50 | 10 | `gold ×1` |
| 30–49 | `diamond` | `EPIC` | 100 | 25 | `diamond ×1` |
| от 50 | `netherite` | `LEGENDARY` | 250 | 100 | `netherite ×1` |

Rate limit хранится в Redis. При временном падении Redis backend переключается
на локальный ограничитель текущего экземпляра и продолжает принимать клики.

## 5. Магазин и покупки

### Каталог

```http
GET /api/v1/shop/catalog
```

Текущий каталог:

| Тип | ID | Цена | Эффект |
|---|---|---:|---|
| `CLICK_UPGRADE` | `click_power_1` | 100 | `+0.5` к базовой силе клика |
| `TOOL` | `wooden_pickaxe` | 250 | множитель урона `×1.2` |
| `TOOL` | `iron_pickaxe` | 800 | множитель урона `×1.8` |
| `MACHINE` | `basic_miner` | 1500 | `10 stone` в час |

`CLICK_UPGRADE` можно покупать повторно; каждая завершённая покупка добавляет
`0.5` к базовой силе клика. Инструменты и машины являются уникальными предметами,
повторная покупка возвращает `PRODUCT_ALREADY_OWNED`.

### Покупка

```http
POST /api/v1/shop/purchase
X-User-Id: <uuid>
Idempotency-Key: <uuid>
Content-Type: application/json

{
  "productType": "TOOL",
  "productId": "wooden_pickaxe"
}
```

Для каждой новой покупки требуется новый `Idempotency-Key`. При сетевой ошибке
тот же запрос необходимо повторить с тем же ключом. Нельзя создавать новый ключ,
пока неизвестен результат предыдущего запроса: это может оформить вторую
допустимую покупку повторяемого улучшения.

Ключ резервируется атомарно в PostgreSQL. Параллельные запросы с одинаковым
ключом не выполняют покупку дважды: проигравший запрос получает сохранённый
результат победившей транзакции. Повторное использование ключа для другого
пользователя или товара возвращает `IDEMPOTENCY_KEY_REUSED`.

Покупка является единой транзакцией:

1. проверяется товар и его серверная цена;
2. проверяется баланс;
3. списываются кредиты;
4. применяется улучшение или добавляется предмет;
5. создаётся запись ledger;
6. обновляются счётчики заданий `spent` и `buys`;
7. сохраняется ответ для последующего replay.

Фронтенд должен использовать `balance` и `clickPower` из `PurchaseResponse`, а
не вычитать цену локально.

## 6. Инвентарь и предметы

```http
GET /api/v1/inventory
X-User-Id: <uuid>
```

Ответ содержит два массива:

- `tools` — купленные инструменты;
- `machines` — купленные машины.

Инструмент содержит:

```json
{
  "toolCode": "iron_pickaxe",
  "powerMultiplier": 1.8,
  "equipped": true,
  "acquiredAt": "2026-11-09T10:00:00Z"
}
```

Одновременно может быть экипирован только один инструмент.

### Экипировка

```http
POST /api/v1/inventory/tools/{toolCode}/equip
X-User-Id: <uuid>
```

Экипировать можно только купленный инструмент. Иначе сервер возвращает
`TOOL_NOT_OWNED`. Ответ содержит:

```json
{
  "equippedToolCode": "iron_pickaxe",
  "baseClickPower": 1.5,
  "toolMultiplier": 1.8,
  "effectiveClickPower": 2.7
}
```

Снять текущий инструмент:

```http
DELETE /api/v1/inventory/tools/equipped
X-User-Id: <uuid>
```

После снятия множитель равен `1.0`.

## 7. Машины и пассивная добыча

Купленная машина изначально не установлена и ничего не производит.

Установить машину:

```http
POST /api/v1/inventory/machines/{machineCode}/install
X-User-Id: <uuid>
```

Отсчёт производства начинается с момента установки. Производство до установки
не начисляется.

Собрать ресурсы со всех установленных машин:

```http
POST /api/v1/inventory/machines/collect
X-User-Id: <uuid>
```

Снять машину:

```http
POST /api/v1/inventory/machines/{machineCode}/uninstall
X-User-Id: <uuid>
```

При снятии сначала начисляется уже накопленный целый объём ресурсов, затем
производство останавливается. Неполный временной остаток сохраняется между
сборами. Максимальное учитываемое офлайн-время — 24 часа.

При входе зарегистрированного пользователя backend автоматически собирает
накопленные ресурсы. Они возвращаются в `AuthResponse.offlineRewards` и
записываются в ledger с `OFFLINE_REWARD`, `resourceCode` и `resourceAmount`.

Ресурсы машин сейчас не увеличивают счётчик задания `earn`: этот счётчик
отражает кредиты, полученные за разрушение блоков.

## 8. Задания

```http
GET /api/v1/challenges
X-User-Id: <uuid>
```

Backend хранит линейный каталог из 60 заданий. Одновременно доступны три первых
задания, за которые ещё не получена награда. После claim освободившееся место
занимает следующее задание.

Каждый элемент `items` содержит:

```json
{
  "index": 0,
  "kind": "clicks",
  "goal": 15.0,
  "reward": 2,
  "current": 15.0,
  "ready": true
}
```

Фронтенд должен строить текст и прогресс по `kind`, `goal`, `current` и `ready`,
а не определять завершённость самостоятельно.

Поддерживаемые типы:

| `kind` | Серверный источник прогресса |
|---|---|
| `clicks` | сумма кликов в принятых неповторных click-batch запросах |
| `break` | количество разрушенных блоков |
| `earn` | кредиты, полученные за разрушение блоков |
| `spend` | сумма цен завершённых покупок |
| `buy` | количество завершённых покупок |
| `level` | `floor(blocksBroken / 2) + 1` |
| `power` | базовая сила клика × множитель экипированного инструмента |

Прогресс глобальный: он считается с начала игры, а не с момента появления
задания в доступной тройке. Награды заданий не увеличивают `earn`.

Получение награды:

```http
POST /api/v1/challenges/{challengeIndex}/claim
X-User-Id: <uuid>
```

Claim разрешён, только если задание входит в текущую доступную тройку, выполнено
и ещё не получено. Операция атомарно:

1. повторно проверяет актуальный прогресс;
2. начисляет награду в кредиты;
3. сохраняет номер задания в `claimed`;
4. пишет `CHALLENGE_REWARD` в ledger;
5. возвращает баланс и обновлённую тройку заданий.

Повторный claim не выдаёт награду и возвращает `CHALLENGE_ALREADY_CLAIMED`.

Ответ списка также содержит:

- `stats` — глобальные счётчики игрока;
- `claimed` — индексы заданий с уже полученной наградой;
- `total` — полное количество заданий в каталоге.

## 9. Правила повторов и восстановления после ошибок

### Click batch

- новый игровой пакет → новый `clientBatchId`;
- потерянный ответ → повторить тот же payload с тем же `clientBatchId`;
- после успешного ответа идентификатор больше не использовать.

### Покупка

- новое намерение купить → новый `Idempotency-Key`;
- таймаут или разрыв соединения → повторить тот же товар с тем же ключом;
- `CONCURRENT_MODIFICATION` → обновить баланс и состояние инвентаря; для
  неизвестного результата сначала повторить прежний ключ, а не создавать новый.

### Остальные операции

Экипировка, установка и снятие машины возвращают итоговое состояние. После
неопределённой сетевой ошибки фронтенд должен перечитать `progress`, `balance`
и `inventory`, прежде чем показывать операцию как завершённую.

## 10. Обслуживание серверных данных

Обработанные `clientBatchId` хранятся 30 дней. Ежедневная задача удаляет более
старые записи. Это означает, что клиент не должен повторять игровые запросы
месячной давности.

Все финансовые операции и награды пишутся в ledger. Идемпотентность, баланс,
инвентарь и задания изменяются в одной транзакции соответствующей игровой
операции.

## 11. Ежедневные награды

Ежедневный календарь использует серверную дату UTC. Пропущенный день не
сбрасывает цикл: игрок продолжает со следующей неполученной награды. После
седьмого дня цикл возвращается к первому.

| День | Награда |
|---:|---|
| 1 | `stone ×10` |
| 2 | `diamond ×1` |
| 3 | `stone ×15`, `diamond ×1` |
| 4 | `stone ×20` |
| 5 | `diamond ×2` |
| 6 | `stone ×25`, `diamond ×2` |
| 7 | `stone ×50`, `diamond ×5` |

Проверить доступность и увидеть текущую награду:

```http
GET /api/v1/daily-rewards/status
X-User-Id: <uuid>
```

Получить награду:

```http
POST /api/v1/daily-rewards/claim
X-User-Id: <uuid>
Idempotency-Key: <uuid>
```

При потере ответа claim нужно повторить с тем же ключом. Сервер вернёт
сохранённый результат, не начисляя ресурсы повторно. Второй claim с другим
ключом в ту же UTC-дату возвращает `DAILY_REWARD_ALREADY_CLAIMED`.

Камни и алмазы начисляются в `player_progress.resources`. Для каждого ресурса
создаётся запись ledger с типом `DAILY_REWARD`. Эти начисления не изменяют
прогресс постоянного задания `earn`.
